LibArchive.Net is licensed under the BSD 2-Clause licence in LICENSE.md. That

How this file is maintained
---------------------------

This file is written and updated by hand. Nothing generates it.

* The component list is derived from the final link command in each
  native/build-*.sh script. Every static library named on a link command has a
  section below, and so does the C library and compiler support code that the
  build toolchains add. Whenever a library is added to or removed from a link
  command, or a build toolchain is changed, update the sections to match.

* The text between "----- BEGIN" and "----- END" markers is copied from the
  named file of the upstream source release pinned in native/build-config.sh
  (for a toolchain component: of the source release its section names). It is
  verbatim, except that whitespace at the ends of lines has been removed. Do
  not edit or re-wrap it.

* Version numbers are deliberately left out of the sections below, so that
  routine dependency updates do not make this file stale. The one exception
  is the record of inspected binaries at the end of this list.
  native/build-config.sh and .github/workflows/build.yml are the record of
  what is built. When a pinned version changes, compare the files named in
  that component's section between the old and the new source release, and
  update the copied text here if they differ.

* Where a licence is given a short name or an SPDX identifier, that is a
  label for convenience only. The reproduced text is what applies.

* Each section says which native binaries it applies to:

    Linux    runtimes/linux-*/native/libarchive.so: six different files.
             linux-x64, linux-arm64 and linux-arm are linked against glibc,
             and linux-musl-x64, linux-musl-arm64 and linux-musl-arm against
             musl. "Linux arm" means the two 32-bit ARM libraries, linux-arm
             and linux-musl-arm, and so on for x64 and arm64.
    macOS    runtimes/osx-*/native/libarchive.dylib (universal x64 + arm64)
    Windows  runtimes/win-*/native/archive.dll (x86, x64, arm64)

* Not listed here: tools that are only used while building, and system
  libraries that the native binaries load at run time but that are not part of
  the package (on Linux the C library that each library is linked against,
  glibc or musl; on macOS the system C library and libiconv; on Windows the
  system DLLs named on the link command, such as kernel32, ws2_32 and bcrypt,
  and the system C runtime).

* The toolchain sections (10 to 15) say what was found in the binaries
  inspected and how, and say so plainly where something could not be
  established. What they say of the macOS library and the Windows DLLs was
  checked against the native binaries of a package built by
  .github/workflows/build.yml before Mbed TLS was added to the Linux builds,
  and what they say of the Linux libraries against the six Linux libraries
  built with zig that are described below. The copied licence texts in those
  sections were compared with the upstream source releases named below and
  in that description. The binaries of that package were built with:

    Linux    Bootlin release stable-2026.08-1, whose manifest names GCC
             15.3.0 and musl 1.2.6 (the earlier Linux libraries; see below)
    Windows  x86 and x64: the Ubuntu 24.04 packages gcc-mingw-w64
             13.2.0-6ubuntu1+26.1 (GCC 13.2.0; the default compilers, which
             use the "win32" thread model) and mingw-w64 11.0.1-3build1
             (MinGW-w64 11.0.1)
             arm64: LLVM-MinGW 20240619, which is built from LLVM 18.1.8 and
             MinGW-w64 commit 7c9cfe6708cafc83c14a2654308b2db62b126eae
    macOS    Apple's toolchain: linker version 1267.0 with the macOS 26.5
             SDK, as recorded in the library itself

  This records what was inspected, not what is built today. When
  native/build-config.sh or .github/workflows/build.yml names a different

1. libarchive
==============================================================================

Applies to:  all native binaries (Linux, macOS, Windows)
Source:      https://www.libarchive.org/ (release pinned in
             native/build-config.sh)
Licence:     BSD 2-Clause for the library as a whole; some files carry other
             terms, as libarchive's own COPYING file sets out below.

The libarchive library is linked in whole (the link commands use
--whole-archive or -force_load). Its sources are the "libarchive" directory of
the source release. The command line programs of that release (bsdtar,
bsdcpio, bsdcat, bsdunzip) are not shipped.

The native binaries for every platform (Linux, macOS and Windows) are built
from modified sources: this project's patches change four of its files.
native/libarchive-narrow-utf8.patch changes libarchive/archive_string.c and
libarchive/archive_write_set_format_zip.c, so that every narrow string is
UTF-8 whatever the locale of the process;
native/libarchive-lz4-init-stream-hc.patch changes
libarchive/archive_write_add_filter_lz4.c, so that it no longer calls a
function that lz4 deprecates; native/libarchive-zip-aes192.patch changes
libarchive/archive_write_set_format_zip.c again, so that it can encrypt with
WinZip AES-192; and native/libarchive-zip-zstd-end-of-entry.patch changes
libarchive/archive_read_support_format_zip.c, so that the ZIP reader ends a
Zstandard entry where the entry's data ends. The patches leave their copyright
notices and licence terms as they are.

The release's README says that code from other projects is kept in its
"3rdparty" directory (code from Project Everest and from p256-m). The build
compiles those files into libmbedcrypto.a as well, but their code is
conditional on options that native/mbedtls-config.h does not set, and none

libraries also credits outside work: a comment in library/sha512.c says that

include.

Verified on the binaries inspected (see "How this file is maintained"): Mbed
TLS code is inside all three libarchive.so files, and the same parts of it in
each. The libraries keep their symbol tables, which record the source file
names of the objects linked in. In each library the objects taken from
libmbedcrypto.a are those of ten files of the release's "library" directory:
aes.c, md.c, md5.c, pkcs5.c, platform_util.c, ripemd160.c, sha1.c, sha256.c,
sha512.c and version.c. Their names come together, directly after those of
the liblz4 objects, which precede libmbedcrypto.a on the link command, and
the static functions and tables listed under them are those of the files of
the same names. Each library defines the same 83 symbols whose names begin
with "mbedtls_" and none whose names begin with "psa_", and leaves no symbol
with either prefix undefined. None of the 83 is exported, as the build
compiles Mbed TLS with -fvisibility=hidden. Each of them is defined by one of
the ten files when the release is compiled, for this check, with
native/mbedtls-config.h. Compiled that way, only two other source files of
libmbedcrypto.a define anything (constant_time.c and version_features.c), and
neither is in the libraries. No file or symbol name from "3rdparty" is in
them, and the arm64 library contains no SHA-512 instruction, so the
accelerated SHA-512 code is not in it. This was established from the symbol
tables and the disassembly; the code was not compared with objects built by
the build's own compilers.

The six Linux libraries built with zig (see "How this file is maintained")
contain the same parts of Mbed TLS, found the same way. In each of them the
objects taken from libmbedcrypto.a are those of the same ten files, named
directly after those of liblz4. Each defines 80 symbols whose names begin
with "mbedtls_" and none whose names begin with "psa_", leaves no symbol with
either prefix undefined, and exports none of them. No file or symbol name
from "3rdparty" is in them, and the arm64 libraries contain no SHA-512
instruction.

Mbed TLS is not inside the macOS library or the three Windows DLLs. The macOS
library keeps its symbol table: neither of its halves defines a symbol whose
name begins with mbedtls_ or psa_, and it leaves its MD5, SHA-1 and SHA-2
digests, HMAC, PBKDF2 and AES to CommonCrypto in /usr/lib/libSystem.B.dylib
(CC_SHA256_Init, CCHmacInit, CCKeyDerivationPBKDF, CCCryptorCreateWithMode
and others). The DLLs are stripped, so they were searched instead for three
things that the Mbed TLS code in the Linux libraries contains: the round
constants of library/sha512.c and of library/sha256.c, and "RIPEMD160", one
of the digest names in library/md.c. The search finds all three in every
Linux library, the two tables at the addresses that the symbol tables give
for them, and the SHA-256 constants a second time, in liblzma's SHA-256 code
(section 4). It finds no SHA-512 constants and no "RIPEMD160" in the DLLs or
in the macOS library, and the SHA-256 constants only once in each DLL and
once in each half of the macOS library, whose symbol table names that copy
as liblzma's. The DLLs take their cryptography from bcrypt.dll (CNG). In the

Applies to:  all native binaries (Linux, macOS, Windows)
Source:      https://github.com/AxioDL/lzokay (commit pinned in

lzokay implements the LZO1X compression format, which libarchive needs to
read and write lzop data. It is what the liblzo2.a named on the link commands
is built from: liblzo2 itself, which is under the GNU General Public License,
is not part of the native binaries. build_lzo_shim in native/build-lzo-shim.sh

interface code. The files in native/lzo-shim are this repository's own code
and, like the rest of it, are under the BSD 2-Clause licence in LICENSE.md,
the licence that the package metadata names.

The build changes one file of lzokay. Before compiling it, build_lzo_shim
applies native/lzo-shim/lzokay-bounds-checks.patch to its copy of
lzokay.cpp. The patch changes three macros, NEEDS_IN, NEEDS_OUT and
CONSUME_ZERO_BYTE_LENGTH, because as published lzokay's decompressor trusts
its input too far: its bounds checks compare "pointer + count" with the end
of a buffer, which can wrap around where pointers are 32 bits wide, and its
scan over a run of zero bytes does not stop at the end of the input, so that
a corrupt or hostile lzop stream could make it read or write outside its
buffers. The patched checks compare the count with the space that is left,
for the compressor's use of NEEDS_OUT as well, and the scan stops at the end
of the input. The patch file says this at its head. lzokay.hpp is compiled
unchanged.

C++ standard library headers. lzokay.cpp and lzo-shim.cpp are C++, and
build_lzo_shim compiles them with -fno-exceptions -fno-rtti
-fno-threadsafe-statics and hidden visibility. The native binaries are not
linked against a C++ runtime library, and every build script checks that the
two object files need none. The files do include headers of the C++
standard library: lzokay.hpp includes <cstddef>, <cstdint> and <memory>,
lzokay.cpp adds <cstring>, <algorithm> and <iterator>, and lzo-shim.cpp adds
<new>. lzokay.cpp uses the function templates std::fill, std::fill_n,
std::copy_n, std::min, std::mismatch, std::begin and std::end, and
lzo-shim.cpp uses placement new, so code from those headers is compiled into
the two objects. That is code compiled from the headers, not code of a C++
runtime library such as libstdc++.a or libc++.a, none of which is in the
binaries (see below). Each build compiles the two files with the headers of
the C++ library of its own toolchain:

    Linux               LLVM libc++ of zig (lib/libcxx of the zig release)
    Windows x86, x64    GNU libstdc++ of the Ubuntu packages
                        g++-mingw-w64-i686-win32 and
                        g++-mingw-w64-x86-64-win32
    Windows arm64       LLVM libc++ of LLVM-MinGW
    macOS               LLVM libc++ of the macOS SDK of Apple's Xcode

Windows arm64: archive.dll is linked by LLVM-MinGW, which is based on Clang.
Its compiler wrappers select LLVM's compiler-rt, not libgcc, as the compiler
support library. The LLVM-MinGW release is pinned by LLVM_MINGW_VERSION in
.github/workflows/build.yml, and the LLVM-MinGW build scripts for that
release pin the LLVM release it is built from. The text below is the file
compiler-rt/LICENSE.TXT of that LLVM release. Check it again whenever
LLVM_MINGW_VERSION changes.

Verified on the binaries inspected (see "How this file is maintained"): one
compiler-rt routine is inside the arm64 archive.dll. It is the stack probe
__chkstk (compiler-rt/lib/builtins/aarch64/chkstk.S), which the code in the
DLL calls from 39 places. Its code is identical to that of the member
chkstk.S.obj of libclang_rt.builtins-aarch64.a in the LLVM-MinGW release, and
its source file is marked "Apache-2.0 WITH LLVM-exception". No other member
of that archive is inside the DLL. Two of its members are too short to be
recognised by their code (int_util.c and the aarch64 cpu_model), but nothing
that refers to them is inside the DLL either. The DLL contains no libunwind,
libc++ or libc++abi code.

The DLL is stripped and has no symbol table, so this was established by
searching it for the code of every member of the release's libraries, after
confirming that the search finds members known to be present. The LLVM-MinGW
download is not pinned by a checksum, in this repository or upstream; the
comparison used the file at the address the workflow downloads from.

Linux arm: zig's compiler-rt, which is inside the two arm libraries (section
14), is not LLVM's, and no LLVM library is linked into any Linux library.

(divsf3.c and divdf3.c), powiXf2.zig (powisf2.c, from LLVM's release 8.0
branch) and clear_cache.zig (which names a commit of llvm-project, and
LLVM's clear_cache.c in a comment). They name no licence. This file takes

macOS: this section does not apply. libarchive.dylib is linked by Apple's
Clang on the build machine, and no compiler-rt code is linked into it.
Verified on the libarchive.dylib of a package built by the CI workflow, for
both the x86-64 and the arm64 half:

* The library keeps its symbol table, local symbols included, so code linked
  in from a static archive would show up by name. No symbol defined in the
  library has the name of a routine defined by libclang_rt.osx.a, the static
  compiler-rt archive that is installed with Apple's Clang. The names
  were taken from the libclang_rt.osx.a of an Apple Command Line Tools
  installation, which is not necessarily the Xcode release that built the
  library.
* The compiler support routines that the library does use (the stack probe
  __chkstk_darwin in the arm64 half and ___chkstk_darwin in the x86-64 half,
  and the stack protector's __stack_chk_fail and __stack_chk_guard) are
  undefined in it and bound to /usr/lib/libSystem.B.dylib. That is a system
  library of macOS and is not part of the package.

The terms on which Apple distributes its compiler-rt were therefore not
looked into. To repeat the check, compare the output of
"nm -arch <arch> -U libarchive.dylib" (what the library defines) with
"nm -arch <arch> -g -U libclang_rt.osx.a", and read
"nm -arch <arch> -m -u libarchive.dylib" (what is left to system libraries).
Check again if native/build-macos.sh or the macOS build image changes.

14. zig's compiler-rt
==============================================================================

Applies to:  Linux arm native binaries (linux-arm and linux-musl-arm)
             (not the Linux x64 and arm64 ones; see below)
Source:      https://ziglang.org/ (the release pinned by ZIG_VERSION in
             native/build-config.sh)
Licence:     MIT licence (SPDX identifier: MIT), in the LICENSE file of the
             zig release, reproduced below; parts are ported from musl
             (section 10) and from LLVM's compiler-rt (section 13)

native/build-linux.sh compiles and links the Linux libraries with zig ("zig
cc" and "zig c++", through native/zig-cc.sh). In place of GCC's libgcc, zig
links its own compiler support library, compiler-rt, into what it links. It
builds compiler-rt for each target, from lib/compiler_rt.zig and the files
of lib/compiler_rt in its release and from the parts of zig's standard
library (lib/std) that they use. It is written in Zig and is not LLVM's
compiler-rt, although some of its files are ported from LLVM's and others
from musl. zig builds it as one object, which the linker takes into a
library only if the library needs one of its symbols, and then whole, as
link_libarchive in native/build-linux-common.sh does not have the linker
discard code that nothing uses.

Verified on the binaries inspected (see "How this file is maintained"):

* linux-arm and linux-musl-arm: zig's compiler-rt is inside both, whole.
  Their symbol tables name its object, "compiler_rt", after all the others,
  and define 852 functions in its code: 426 local to the object, named after
  their source files (such as compiler_rt.count0bits.__clzsi2_arm32), and
  426 others, among them the routines of the ARM run-time ABI, such as
  __aeabi_uldivmod (64-bit unsigned division), which the code of
  libarchive, zlib and Zstandard in the libraries calls. Its code, about
  180 KiB, comes last in each library, and is as long as the code of the
  object in zig's cache from the build, apart from alignment. Each library
  also held the debugging information of that object, and of nothing
  else, which names zig as its producer (native/build-linux.sh now strips
  it; see "How this file is maintained"). Its line tables give code to 82
  source files of the zig release: lib/compiler_rt.zig, 67 files of
  lib/compiler_rt and 14 of lib/std. The stack protector's guard of these
  libraries is not compiler-rt's but that of native/linux-arm-stack-guard.c,
  which is this project's own; compiler-rt's __stack_chk_fail is the one
  that they use.
* linux-x64, linux-arm64, linux-musl-x64 and linux-musl-arm64: none of it.
  zig built compiler-rt for these links as well (the cache of each build
  holds the object, with its debugging information), but none of the names
  that the object defines (1,795 for x64 and 1,146 for arm64) is defined in
  these libraries, their symbol tables name no compiler_rt object, and they
  hold none of its debugging information.

Where parts of it come from: of the 82 source files, 19 say that they are
ported from musl (section 10 names them), one that the "Logic and flow" of
two of its functions are "heavily inspired by MUSL fmodl"
(lib/compiler_rt/fmod.zig), and six that they are ported from LLVM's
compiler-rt (section 13 names them). Those sections reproduce the licences
of musl and of LLVM's compiler-rt. One of the 19, lib/compiler_rt/tan.zig,
also gives the address of the Go project's math/tan.go among its sources,
without saying what it takes from it. The Go project's licence is not in
the zig release, and this file records the point without resolving it.
Other comments name published methods that the code follows, such as Bit
Twiddling Hacks, Hacker's Delight, Knuth's Algorithm D, Annex G of the C
standard and papers by Ping Tak Peter Tang; they name no licence. None of
the 82 files carries a licence statement or a copyright notice other than
those notes, and zig's own licence is the LICENSE file of its release,
reproduced here.

15. GNU C Library (glibc)
==============================================================================

Applies to:  Linux x64 and arm64 native binaries linked against glibc
             (linux-x64 and linux-arm64; not linux-arm, and not the
             linux-musl-* ones)
Source:      https://www.gnu.org/software/libc/ (the copies of its sources
             in the zig release pinned by ZIG_VERSION in
             native/build-config.sh)
Licence:     GNU Lesser General Public License, version 2.1 or later, with
             unlimited permission to link the compiled files with other
             programs and to distribute those programs, as the notice of
             each file says (SPDX identifier of the licence:
             LGPL-2.1-or-later)

The glibc libraries are linked dynamically against glibc: libc.so.6 and the
other glibc libraries that they need come from the system, not from the
package. As glibc's own toolchain does, zig also links each of them against
glibc's static libc_nonshared.a, which zig builds for the glibc version of
the target from the copies of glibc's sources in lib/libc/glibc of its
release. Before glibc 2.33, stat, fstat, lstat, fstatat and mknod, and their
64-bit forms, were not functions of libc.so.6 but small functions of
libc_nonshared.a, linked into the programs and libraries that call them:
each passes its arguments on, with the version number of the interface, to
a function of libc.so.6 (__xstat, __fxstat, __xmknod and the like).
linux-x64 and linux-arm64 are built for glibc 2.28 (see
native/build-linux.sh), so they contain those of these functions that they
call. linux-arm is built for glibc 2.34, whose libc.so.6 has them all.

Verified on the binaries inspected (see "How this file is maintained"):

* linux-x64 and linux-arm64: six members of libc_nonshared.a are inside
  each of them, compiled from the files io/stat-2.32.c, io/fstat-2.32.c,
  io/lstat-2.32.c, io/stat64-2.32.c, io/fstatat-2.32.c and io/mknod-2.32.c
  of lib/libc/glibc of the zig release, the files that zig compiles for a
  glibc older than 2.33. Their symbol tables name those six files, after the
  objects of every library on the link command, and define stat, fstat,
  lstat, stat64, fstatat and mknod (with the aliases __stat, __fstat,
  __lstat and __mknod), 16 to 52 bytes of code each and local to the
  library; the libraries import from libc.so.6 the functions that these
  call, __xstat, __fxstat, __lxstat, __xstat64, __fxstatat and __xmknod.
  Each library also held the debugging information of these six objects,
  and of nothing else, which names the same six files (now stripped, as
  section 14 says). The other members of the libc_nonshared.a that zig
  built for these links (atexit, at_quick_exit, pthread_atfork,
  stack_chk_fail_local, fstat64, lstat64, fstatat64, mknodat and elf-init)
  are not in them.
* linux-arm: no glibc code. It imports these functions from libc.so.6, in
  their forms with a 64-bit time_t (__stat64_time64 and the like) and
  mknod under its own name, and contains none of the members of the
  libc_nonshared.a that zig builds for its glibc version (atexit,
  at_quick_exit, pthread_atfork and stack_chk_fail_local).
* No Linux library contains glibc's start-up code: as section 10 says, none
  has a .init or .fini section or an _init or _fini function, which glibc's
  crti.o and crtn.o would bring.

fstatat-2.32.c and 1995-2020 in mknod-2.32.c. The GNU Lesser General Public
